Zoé — le socle

Vous écrivez le sens. Zoé porte les états. La peau peint. Trois mots dans votre HTML, et vous obtenez un élément complet — vivant, accessible, animé, indexable. Cette page en est la preuve : elle est écrite en HTML nu, et c'est la peau qui l'habille.

La promesse, en une ligne

<z-checkbox name="lettre">Recevoir la lettre</z-checkbox>

Pas de <div> de structure, pas de JavaScript à câbler. La case réagit (survol, appui, focus, cochée), elle part dans un <form>, elle se laisse habiller par n'importe quelle peau. Vous n'avez écrit que le sens.

Le partage : HTML · CSS · Zoé

Toute Zoé tient dans cette répartition. Chacun son rôle, jamais l'un dans l'autre :

La couchePorte…Lue par les moteurs ?
HTMLle sens (le texte, le rôle, les pièces que vous écrivez)oui
CSSle dessin (la peau, le mouvement)non
Zoéle vivant (les états), l'accessibilité, le formulaire—

Le HTML est pour les moteurs. Le CSS est pour l'œil. Zoé fait tenir les deux.

Le référencement est un acquis, pas un combat

Le contenu reste natif : un titre est un <h1>, un lien un <a href>, un paragraphe un <p>. Les moteurs — et les IA qui lisent le HTML source — les voient tout de suite, sans JavaScript. C'est le light DOM : Zoé n'enferme rien dans un shadow root et n'injecte aucune balise. La peau habille le natif, elle ne le remplace jamais.

Seuls les widgets — boutons, cases, curseurs, onglets, boîtes de dialogue, ce qui n'a aucune valeur pour l'index — deviennent des z-*. La règle tient en une bascule :

Lu par les moteurs → natif, habillé par la peau. Cliqué → z-*.

Les états : des mots que le navigateur connaît

Chaque élément Zoé pose lui-même ce qui lui arrive — over, press, release, releaseOut, drag, focus, current, loading, error, success… — en :state(), le sélecteur natif prévu pour les custom elements. Vous ne gérez rien ; vous peignez : 

z-button:state(over)    { --z-button--background__color: var(--z-accent-soft); }
z-button:state(press)   { scale: .97; }
z-button:state(loading) { opacity: .6; }

Les états durables sont des attributs : <z-button loading> en HTML, btn.setState("loading") en JavaScript, :state(loading) en CSS — une seule vérité, trois façons de la lire.

Les calques : ce que vous écrivez, Zoé le peint

Un composant s'écrit de deux façons. Court, une ligne, le CSS peint l'hôte. En calques, chaque pièce est un <z-layer part="…"> que vous écrivez vous-même — donc chaque pièce peut bouger seule : 

<z-checkbox>
  <z-layer part="background"></z-layer>
  <z-layer part="marker">
    <z-layer part="ring"></z-layer>
    <z-layer part="dot"></z-layer>
  </z-layer>
  <z-layer part="infos">
    <z-layer part="label">Recevoir la lettre</z-layer>
  </z-layer>
  <z-layer part="contact"></z-layer>
</z-checkbox>

Les deux formes lisent les mêmes tokens et se comportent pareil. Le lexique est partagé : background, marker, ring, dot, infos, label, contact veulent dire la même chose dans chaque composant — c'est ce qui permet à une peau de peindre un composant qu'elle ne connaît pas. Zoé ne génère jamais un calque : ce que vous écrivez est ce que vous déboguez.

Le pacte : une grammaire, pas un dictionnaire

--z-{composant}[--{pièce}]__{propriété-css}      ce que l'on peint
z-{composant}:state({état})                      quand

Les frontières sont doublées (-- entre le composant et la pièce, __ avant la propriété), les mots restent simples. Le nom de n'importe quoi se déduit, il ne se mémorise pas — pour vous comme pour une IA. Un état ne repeint pas : il redéfinit une swatch, et tout ce qui la boit suit, sans fuir vers les voisins. 

z-checkbox:state(current) { --z-checkbox--marker__background-checked: #ff2d55; }

La peau : un fichier, tout change

Une peau est un fichier CSS de tokens (--z-accent, --z-surface, --z-radius, --z-font…) posés sur :root, plus la couche qui habille le HTML natif. Changer de peau, c'est changer un <link>. Deux peaux sont livrées — HighTech, la planche d'ingénieur, et Claude, l'encre chaude — et le sélecteur en haut à droite de chaque page les échange en direct.

Les outils : des nombres donnés au CSS

  • <z-contact> — une balise dans la page, et chaque clic reçoit l'effet signé par la peau, au point de contact.
  • channel="nom" — deux éléments reliés par un nom : ce qui change ici arrive là-bas, en variable CSS. C'est le CSS qui décide quoi en faire.
  • les capteurs — <z-pointer>, <z-scroll>, <z-inview>, <z-size>, <z-drag> posent des nombres nus ; un nombre se multiplie en distance, en angle, en opacité.
  • z-motion — les mouvements partagés (pop, shake, ripple…), à brancher sur n'importe quel état.

Pour les IA, et pour l'éditeur

Tout ce qui précède est généré depuis le code, jamais maintenu à la main : la grammaire, le llms.txt à la racine, le manifeste standard, l'autocomplétion VS Code — et un serveur MCP qui donne à un agent la fiche de chaque élément, une recherche dans le vocabulaire et un vérificateur. En développement, z-lint signale dans la console toute balise, attribut, état ou token mal écrit, avec le nom valide le plus proche.

Le pacte, côté socle

Cette base est figée. On ne la redessine pas — on compose par-dessus. Le socle porte tout ce que vous imaginez, à condition qu'on le laisse tranquille et qu'on bâtisse dessus plutôt que de le refaire.

Sous le capot, le socle tient en peu de fichiers — core/z-element (le vivant : états, formulaire, déclencheurs) · core/z-layer (le calque) · zoe.css et zoe.js (les points d'entrée). Chaque composant, lui, reste maigre : il dit seulement « je suis un bouton ».
